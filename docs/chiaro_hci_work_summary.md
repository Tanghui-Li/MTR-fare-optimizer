# Chiaro 实现部分与 HCI 原则总结

Last updated: 2026-06-14

本文档用于总结郎若谷在本项目中的实现工作，并将这些工作与 HCI 课程中的核心原则对应起来。我负责的是项目中的「周边探索（Nearby Explore）」垂直功能：在他人搭建好的港铁地图与票价骨架之上，从零设计并落地了一条「站点周边美食 / 景点」的完整链路——后端自建多源开放数据离线管线，前端实现探索面板、POI 卡片、地图图层、收藏与「逛吃路线」规划，并做到三语本地化、版权合规署名与运行时零外网依赖。

## 一句话总结

我的实现重点是回答用户出行后真正会问的一个问题——**「到站之后，附近能吃什么、能逛什么，值不值得去、怎么走过去」**，并让用户在不离开本应用、不依赖任何商业地图 App 的前提下完成这件事：

- 看得到：到站即可看到周边餐饮 / 景点，带真实照片、评分、距离与步行时长。
- 选得动：按类别、菜系、距离、评分自由筛选排序，收藏感兴趣的店。
- 走得通：把选中的几个点串成一条最近邻步行「逛吃路线」，在地图上看清怎么走、大约要多久。

## 1. 离线数据管线：把开放数据变成可信、可缓存、零外网依赖的内容

### 实现内容

我设计了一条三段式的离线数据管线，所有数据均来自版权干净的开放来源，**构建期一次性抓取，前端运行时完全不访问外网**：

- `scripts/build_pois.py`：从 **OpenStreetMap（Overpass API）** 按车站 800m 半径抓取餐饮（restaurant / cafe / fast_food）与景点（museum / viewpoint / gallery / attraction 等），做去重、归站、距离与步行时长计算、菜系（cuisine）归一化，并合成一个「**信息完整度 + 距离**」的客观推荐分。
- `scripts/enrich_pois.py`：为拥有维基条目的 POI 补充**真实照片与真实简介**，链路为 OSM → Wikidata（P18 主图）→ Wikipedia Summary（首段摘要）→ Wikimedia Commons（缩略图 + 作者 + 授权）。刻意**跳过连锁品牌**，避免每家分店都显示同一品牌 logo。
- `scripts/fetch_apify.py`：用 **Apify Google Maps Scraper** 为核心站点灌入真实美食数据（⭐评分 / 评论数 / 价位 / 照片），并按站点重要度分配抓取配额；对已有维基简介的名店做「简介认领」，让名店在换用 Google 数据后不丢失介绍。

最终产物：`src/data/pois.json` 收录约 **96 个车站、2500+ 个 POI**，其中绝大多数带真实照片与真实评分，约 2100+ 张图片落地到 `public/poi/`。

### 解决的问题

「周边推荐」最容易做成两种失败形态：一是只显示一堆没有名字、没有图、没有评分的点，用户根本无从判断值不值得去；二是直接调用商业地图 API，既有第三方依赖与配额问题，又和本项目「仅使用开放数据」的定位冲突。我要在「内容足够丰富可信」与「不引入运行时外部依赖」之间取得平衡。

### 对应 HCI 原则

- 系统可信度：照片、评分、营业时间、来源标注让推荐有据可查，而不是凭空生成。
- 现实世界映射：距离、步行分钟、真实店名与真实照片，对应用户在现实中会看到的东西。
- 性能即体验：图片与数据全部本地化，首屏与切换站点无需等待网络，交互即时。
- 诚实表达：推荐分被明确定义为「信息完整度 + 距离」的客观信号，而非伪造的星级评分，避免误导。

### 汇报时可这样讲

> 我没有直接接商业地图 API，而是自己搭了一条离线数据管线，把 OpenStreetMap、Wikidata、维基百科和 Google 评分整合进来，构建期抓一次、图片落到本地，运行时零外网依赖。这样既符合项目「只用开放数据」的定位，又能让每个推荐都带真实照片、评分和来源。

## 2. 周边探索面板：让用户主导「看什么、怎么排」

### 实现内容

`NearbyPanel.tsx` 是周边探索的侧边面板，提供：类别分段切换（全部 / 美食 / 景点，带数量角标）、排序切换（推荐 / 距离 / 评分）、半径滑块（200–800m，默认 500m）、菜系 chips 筛选（按当前半径内出现的菜系动态生成）、随机推荐、仅看收藏过滤，以及结果数量的实时提示。当筛选后无结果但抓取范围内仍有点时，空态会给出「**扩大半径到 XXXm → 可见 N 个**」的一键引导按钮。

### 解决的问题

「附近有什么」对不同用户意味着完全不同的需求：有人只想快速吃饭，有人专门找景点，有人想喝杯咖啡，有人愿意多走几百米换更好的选择。如果只给一个固定列表，用户就被迫在大量无关项里翻找。面板需要把「筛选 / 排序 / 范围」的控制权交给用户，并在「筛空了」时帮用户找到出路而不是甩一个死胡同。

### 对应 HCI 原则

- 用户控制与自由：类别、菜系、排序、半径、仅看收藏全部由用户即时调整。
- 灵活性与效率：排序与菜系 chips 让熟练用户一步到位；随机推荐照顾「选择困难」的场景。
- 容错与帮助用户：空态不止是「无结果」，而是给出扩大半径的可执行建议。
- 状态可见性：类别角标、菜系计数、结果数量实时反映当前筛选下还剩多少选择。

### 汇报时可这样讲

> 「附近有什么」对每个人意思都不一样，所以我把控制权交给用户：可以按类别、菜系、距离、评分自由筛选排序。而且当筛选筛空时，我没有只显示「无结果」，而是告诉用户「把半径扩大到多少就能看到几个」，给一个能直接点的出路。

## 3. POI 卡片与详情：用渐进式披露兼顾「扫一眼」与「看仔细」

### 实现内容

`PoiCard.tsx` 默认是紧凑卡片：缩略图 + 名称 + 类别标签 + 距离 / 步行时长 + 评分或推荐星条；点击展开后才显示大图（带作者署名与来源链接）、简介、营业时间，以及定位、加入逛吃路线、官网、电话、维基百科等操作。`PoiThumb.tsx` 负责缩略图：有真实照片时懒加载并淡入，**加载失败或无图时回退到按菜系确定性着色的渐变 + emoji 占位图**（同一店铺永远得到同一外观，靠 `stableHash` 对色相做微扰），保证视觉稳定又不单调。

### 解决的问题

信息密度是个两难：列表要能让用户快速扫读比较，但用户选中某一项时又想看到照片、简介、营业时间和联系方式。如果全部信息一直铺开，列表会变得冗长难比较；如果信息太少，用户又得跳出去查。同时还要处理「很多店没有照片」的现实——不能让缺图的卡片显得破碎。

### 对应 HCI 原则

- 渐进式披露：列表只放决策必需信息，详情按需展开，避免信息过载。
- 识别优于记忆：照片、emoji、评分、距离让用户「认出」而不是「回忆」每个点。
- 美学与极简设计：缺图时的确定性渐变占位让界面始终完整、克制、有秩序。
- 可信度与诚实：照片标注作者与授权、详情底部标注数据来源（Google Maps / OpenStreetMap / Wikipedia），让用户知道信息从哪来。

### 汇报时可这样讲

> 卡片我用了渐进式披露：列表里只放扫一眼要比较的东西——图、名字、距离、评分；点开才看大图、简介和营业时间。很多店没有照片，我没让它们显示成破图，而是回退到按菜系上色的占位图，同一家店永远长一个样，界面始终是完整的。

## 4. 地图图层联动：让「列表里的选择」和「地图上的位置」互相印证

### 实现内容

`PoiLayer.tsx` 在地图上渲染：当前站点的半径圆、按类别用 emoji 区分的 POI 标记、选中项的飞行定位与高亮、以及逛吃路线的虚线连线；在 `MapView.tsx` 中，**有周边数据的车站会在站点标记后方叠一层柔光环**作为「这里可以探索」的暗示，点击即可拉起面板。列表与地图双向联动：点列表卡片地图飞过去并高亮，点地图标记列表自动滚动到对应卡片。

### 解决的问题

「附近探索」本质是空间任务，纯列表无法回答「这个点在车站的哪个方向、离我多远、几个点之间顺不顺路」。如果列表和地图各管各的，用户就得在两者之间反复对照、自己脑补位置关系，认知负担很高。

### 对应 HCI 原则

- 现实世界映射：半径圆、真实坐标、步行时长把抽象列表还原成真实空间关系。
- 系统反馈：选中 / 定位时的平滑飞行与高亮，让用户清楚「我点的是哪个」。
- 一致性：菜系 / 类别的 emoji 与配色在卡片标签、缩略图占位、地图标记三处保持统一。
- 降低认知负荷：柔光环把「哪些站值得点开探索」直接可视化，用户不必逐站试。

### 汇报时可这样讲

> 周边探索本质是个空间问题，所以我把列表和地图做成双向联动：点卡片地图飞过去高亮，点地图标记列表自动滚到对应卡片。有内容的车站我还在背后加了一圈柔光，等于直接告诉用户「这一站点开有东西可看」。

## 5. 逛吃路线规划：从「一堆点」到「一条能照着走的路线」

### 实现内容

用户可把多个 POI 加入「逛吃路线」。我用**从车站出发的最近邻贪心排序**把这些点串成一个合理的步行顺序，估算整条路线的步行总时长，并在地图上以虚线把「车站 → 各点」依次连起来；面板底部用编号 chips 展示路线顺序，点 chip 可直接定位到对应点。

### 解决的问题

用户收藏或挑出几个想去的地方之后，真正的问题是「**先去哪个、后去哪个，怎么走最省脚力，总共大概要多久**」。如果只是把选中的点散落在地图上，用户还得自己规划顺序，这正是出行场景里最累的一步。

### 对应 HCI 原则

- 现实世界映射：最近邻排序贴近人真实的「就近顺路逛」直觉，总时长给出可预期的成本。
- 识别优于记忆：编号 chips + 地图虚线让用户一眼看清顺序，不用记「我选了哪几个」。
- 用户控制：路线可随时增删、清空，顺序随选择自动重算。
- 反馈：每次增删立即更新连线与总时长，操作后果即时可见。

### 汇报时可这样讲

> 用户挑出几个想去的点之后，最累的其实是排顺序。我用最近邻算法从车站出发把它们串成一条顺路的步行路线，估出总共大概走多少分钟，在地图上用虚线连起来。用户不用自己规划，照着编号走就行。

## 6. 收藏、三语与视觉一致性：把功能做成「可长期用、谁都能用」

### 实现内容

收藏夹通过 `localStorage` 持久化（`mtr.poi.favorites`），刷新后仍在，并支持「仅看收藏」过滤与计数角标。整套功能覆盖繁体中文、英文、简体中文三语，POI 名称按语言回退并显示次要名称（中文界面补英文名、英文界面补中文名）。`cuisineMap.ts` 把每个菜系 / 景点类别统一映射到「三语名称 + emoji + 主色相」，作为卡片标签、占位缩略图配色和地图标记图标的单一数据源。同时为面板与卡片补齐了 `role` / `aria-*` / 实时区域（`aria-live`）与键盘 ESC 关闭等无障碍属性。

### 解决的问题

一个演示型功能和一个「真的能用」的功能差别在于：收藏会不会丢、换语言会不会有半截没翻译、同一个菜系在卡片和地图上是不是同一个图标同一种颜色、用键盘和读屏能不能操作。这些细节不解决，功能就只是「看起来能用」。

### 对应 HCI 原则

- 一致性与标准：菜系→emoji + 配色单一来源，保证三处视觉表达永远一致。
- 国际化与可理解性：三语覆盖核心流程，名称按语言智能回退。
- 用户控制与效率：收藏持久化 + 仅看收藏，支持用户跨会话管理自己的兴趣点。
- 包容性设计：语义化角色、实时状态播报与键盘操作，照顾读屏与键盘用户。

### 汇报时可这样讲

> 我把这个功能当成「真的会被用」来做：收藏存到本地刷新不丢，三语文案全部覆盖，每个菜系在卡片和地图上都是同一个 emoji、同一种颜色，并且补齐了 aria 属性和键盘操作。这些细节决定了它是「能演示」还是「能用」。

## 可用于汇报的个人总结

我的工作在项目里承担了「**到站之后**」这一段体验：当其他模块帮用户算出怎么最省钱、怎么到达目的地之后，我的功能接着回答「那么，到了之后干什么」。具体来说：

- 后端我搭了一条三段式离线数据管线，把 OpenStreetMap、Wikidata、维基百科和 Google 评分整合成本地数据，运行时零外网依赖，既丰富又可信。
- 前端我做了探索面板、POI 卡片、地图图层和逛吃路线四块，用渐进式披露兼顾「扫读比较」和「看仔细」，用列表 / 地图双向联动把空间关系讲清楚。
- 收藏持久化、三语本地化、统一视觉编码和无障碍属性，让它从「能演示的 demo」变成「真的能用的功能」。

因此，我的实现与 HCI 的结合点可以概括为：**用真实数据建立信任，用渐进式披露控制信息密度，用空间联动降低认知负担，用筛选 / 收藏 / 路线把控制权交还用户。**

## 汇报时建议强调的三句话

1. 我的部分回答的是「到站之后干什么」——把出行的终点变成体验的起点，而不是只停在「算出票价」。
2. 我没有接商业地图 API，而是自建离线数据管线，让每个推荐都带真实照片、评分和来源，且运行时不依赖任何外网。
3. 探索面板、地图联动和逛吃路线共同体现了 HCI 中的用户控制、渐进式披露、现实世界映射和系统可信度。
