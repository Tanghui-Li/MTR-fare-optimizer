# fanqi 新增功能贡献说明

本文档用于说明本人在原始 `MTR-fare-optimizer` 项目基础上完成的主要新增内容。整体目标是将项目从一个“能够计算最低票价的工具”，进一步升级为一个能够综合考虑票价、时间、行动能力、额外出入闸成本和用户偏好的“真实交通决策系统”。

## 1. 新增内容总览

本次新增内容围绕三个核心功能展开：

1. **无障碍友好路线规划**
   - 将站点无障碍设施数据纳入路线评估。
   - 支持“关闭 / 优先 / 必须满足”三种无障碍策略。
   - 在智能推荐中显示无障碍匹配度，提升路线对老人、轮椅用户、携带行李者、推婴儿车者等人群的友好程度。

2. **时间 / 票价折中路线**
   - 不再只计算最低票价，而是同时生成最低价、最快、折中、常规路线等候选方案。
   - 根据用户选择的优化目标，对票价、预计耗时、换乘、出入闸次数等因素进行综合评分。
   - 使系统从“理论上最便宜”转向“现实中更值得走”。

3. **少出闸 / 节省阈值模式**
   - 允许用户设置最多接受多少次额外出入闸。
   - 允许用户设置最低节省金额阈值。
   - 当省钱收益过低或出入闸负担过高时，系统自动回退到更稳妥的常规路线。

此外，为了支撑上述功能，我还补充完成了：

- 智能推荐评分与解释模块。
- 路线指标计算模块。
- 控制面板中的路线偏好设置 UI。
- 智能推荐结果面板。
- 票价比较栏的语义优化，将“最佳票价”拆分为“最低票价 / 推荐票价 / 一般票价”。
- 与现有地图、路线卡、移动端面板的状态同步。

## 2. 设计目标与 HCI 动机

原始项目已经能够计算港铁票价优化路线，但它的核心逻辑更接近“最低价格求解器”。在真实出行场景中，用户并不总是选择最低票价路线。用户还会考虑：

- 是否需要额外出闸再入闸。
- 节省金额是否值得多走、多换乘、多操作。
- 预计耗时是否明显增加。
- 站点是否有电梯、无障碍通道等设施。
- 是否携带行李、推婴儿车，或者行动能力有限。
- 是否希望快速、稳定、少思考地完成行程。

因此，本次新增功能的核心设计目标是：

> 将路线规划从“单目标最低价优化”扩展为“多目标、人群适配、可解释的交通决策推荐”。

从《人机交互导论》的角度看，本次新增内容主要对应以下可用性原则：

| 可用性原则 | 在本项目中的体现 |
| --- | --- |
| 可学习性 | 使用清晰的票价比较、智能推荐面板和路线卡说明推荐理由，降低理解门槛。 |
| 效率 | 系统自动生成多个候选路线，用户无需人工试算不同分段方案。 |
| 鲁棒性 | 当约束无法满足或节省收益不足时，保留常规路线作为回退方案。 |
| 可控性 | 用户可以设置优化目标、无障碍策略、出入闸次数和节省阈值。 |
| 反馈可见性 | 展示预计耗时、无障碍匹配度、节省金额、出入闸次数等关键指标。 |
| 包容性 | 将无障碍设施纳入路线推荐，照顾行动能力不同的用户。 |

## 4. 路线候选生成机制

相关文件：

- `src/routePlanner.ts`
- `src/utils/algorithms.ts`
- `src/utils/graphBuilder.ts`

### 4.1 从单一路线扩展为候选路线集合

原始项目主要关注“优化路线”和“常规路线”之间的比较。本次新增了候选路线集合函数：

```ts
export function findRouteCandidateSet(...)
```

它会生成四类候选路线：

| 候选路线 | 说明 |
| --- | --- |
| `lowestFare` | 以最低票价为目标生成的优化路线。 |
| `regular` | 常规乘车路线，作为用户熟悉且稳妥的基准方案。 |
| `fastest` | 更偏向时间效率的路线。 |
| `balanced` | 在票价与时间之间折中的路线。 |

这样做的意义是，系统不再直接把最低票价作为最终推荐，而是先生成一组候选，再结合用户偏好选择最合适的方案。

### 4.2 路线搜索评分函数

新增 `getScoreEdge(goal)`，根据不同目标返回不同的边权重计算方式。

#### 票价优先

```ts
return edge.fare + minutes * 0.03 + gatePenalty * 0.2 + transferPenalty * 0.1;
```

特点：

- 票价是最主要因素。
- 时间、出入闸、换乘只作为轻微惩罚。
- 适合价格敏感型用户。

#### 时间优先

```ts
return minutes + edge.fare * 0.16 + gatePenalty + transferPenalty;
```

特点：

- 预计耗时是最主要因素。
- 票价仍然会影响结果，但权重较低。
- 出入闸与换乘会明显增加成本。

#### 综合平衡

```ts
return edge.fare * 0.7 + minutes * 0.65 + gatePenalty * 2 + transferPenalty;
```

特点：

- 票价和时间接近同等重要。
- 对出入闸有更高惩罚。
- 更符合一般用户“不想太麻烦，但也想省一点”的心理。

### 4.3 边级预计耗时

在 `src/utils/graphBuilder.ts` 中为图边加入 `estimatedMinutes`：

| 交通方式 | 默认边耗时 |
| --- | --- |
| `TRANSFER` | 5 分钟 |
| `AEL` | 8 分钟 |
| `LRT` | 7 分钟 |
| `NWBUS` / `TAIPOBUS` | 10 分钟 |
| `MTR` | 6 分钟 |

该字段主要用于路线搜索阶段，使“最快路线”和“折中路线”能够在图搜索时感知时间成本。

### 4.4 出入闸约束

在 `src/utils/algorithms.ts` 中为 Dijkstra 搜索状态加入 `gateChanges`，并增加 `maxGateChanges` 约束。

作用：

- 用户可以要求系统不要推荐过多次出闸再入闸的方案。
- 当路径搜索过程中发现出入闸次数超过用户设置上限时，提前剪枝。
- 这使得“少出闸模式”不仅是展示层功能，而是进入了路线搜索逻辑。

## 5. 智能推荐与路线指标模块

新增核心文件：

- `src/utils/routeInsights.ts`

该文件承担了三个职责：

1. 计算路线指标。
2. 根据用户偏好选择推荐路线。
3. 生成推荐理由和权衡提示。

### 5.1 出入闸次数计算

函数：

```ts
export function getRouteGateChanges(segments?: DetailedSegment[]): number
```

当前实现：

```ts
return Math.max((segments?.length ?? 0) - 1, 0);
```

含义：

- 如果路线只有 1 个分段，则额外出入闸次数为 0。
- 如果路线有 2 个分段，则额外出入闸次数为 1。
- 如果路线有 3 个分段，则额外出入闸次数为 2。

这里统计的不是“总刷闸次数”，而是相对于一次完整乘车而言，用户需要额外执行的分段操作次数。

### 5.2 预计耗时估算

函数：

```ts
export function estimateRouteMinutes(segments?: DetailedSegment[]): number
```

估算逻辑：

```ts
预计耗时 =
  出入闸次数 * 4
  + 每段路线默认等待时间
  + 每段路线站点跳数 * 单跳耗时
```

默认等待时间：

| 交通方式 | 等待时间 |
| --- | --- |
| `MTR` | 3 分钟 |
| `AEL` | 6 分钟 |
| `LRT` | 4 分钟 |
| `NWBUS` / `TAIPOBUS` | 7 分钟 |
| `TRANSFER` | 4 分钟 |

单跳耗时：

| 交通方式 | 单跳耗时 |
| --- | --- |
| `AEL` | 4 分钟 |
| `LRT` | 2.4 分钟 |
| `NWBUS` / `TAIPOBUS` | 3 分钟 |
| `MTR` | 2 分钟 |

设计意义：

- 虽然当前不是实时班次级精确预测，但它可以为“最低价路线”和“常规路线”的时间成本提供可比较依据。
- 用户能直观看到“多省多少钱”和“多花多少时间”之间的关系。

### 5.3 无障碍匹配计算

函数：

```ts
function hasAccessibilityFacilities(stationId: string, filter: string[][]): boolean
```

数据来源：

- `src/data/accessibilityData.json`

计算逻辑：

- 若无障碍筛选为空，则默认满足。
- 对巴士和轻铁节点暂时视为满足，避免因数据缺失导致路线完全不可用。
- 对 MTR 站点，检查站点是否具备用户筛选的无障碍设施。
- 支持条件组合：每组内部是“或”，组与组之间是“且”。

在路线指标中体现为：

| 指标 | 含义 |
| --- | --- |
| `accessibilityMatchedStops` | 路线中满足无障碍条件的站点数。 |
| `accessibilityProblemStops` | 路线中不满足条件的站点数。 |
| `accessibilityScore` | 满足条件站点占比。 |

### 5.4 路线综合评分

函数：

```ts
export function evaluateRoute(...)
```

该函数会把路线转换成一组综合指标：

- 总票价。
- 预计耗时。
- 出入闸次数。
- 换乘次数。
- 站点数量。
- 无障碍匹配情况。
- 综合评分 `score`。

评分中包含以下惩罚项：

| 惩罚项 | 作用 |
| --- | --- |
| `accessibilityPenalty` | 当路线不满足无障碍偏好时增加成本。 |
| `gatePenalty` | 出入闸次数越多，推荐成本越高。 |
| `transferPenalty` | 换乘越多，推荐成本越高。 |

其中，当无障碍模式为 `require` 时，不满足条件的站点会被赋予很高惩罚，从而使其难以被推荐。

### 5.5 推荐路线选择

函数：

```ts
export function selectRecommendedRoute(...)
```

工作流程：

1. 分别计算 `lowestFare`、`regular`、`fastest`、`balanced` 四类候选路线指标。
2. 过滤掉不可达路线。
3. 根据 `maxGateChanges` 和 `accessibilityMode` 过滤不符合用户约束的路线。
4. 在可用候选中选择综合评分最低者。
5. 如果用户设置了最低节省金额，并且当前省钱路线节省不足，则回退到常规路线。
6. 输出推荐结果和 `RouteInsight` 解释对象。

### 5.6 节省阈值回退逻辑

核心逻辑：

```ts
if (
  preferences.minSavings > 0 &&
  selected.metrics.gateChanges > 0 &&
  selectedSavings < preferences.minSavings &&
  canUseRoute(regularMetrics, preferences)
) {
  selected = { result: candidates.regular, metrics: regularMetrics };
  suppressedSavings = true;
}
```

用户价值：

- 避免“为了省 0.5 港币而多次出闸”的不合理推荐。
- 将用户的心理阈值显式纳入算法。
- 更符合真实出行中的成本收益判断。

### 5.7 推荐解释文本

文件中还新增：

- `getReasonText(...)`
- `getTradeoffText(...)`

用于把推荐结果转化为可读解释，例如：

- 因为票价最低而推荐。
- 因为时间优先而推荐。
- 因为满足无障碍条件而推荐。
- 因为节省金额不足，所以忽略复杂省钱路线。
- 路线接近最快候选。
- 路线接近最低价候选。

这部分增强了系统的可解释性，使用户更容易理解系统为何推荐某条路线。

### 7.2 三栏票价比较

原有票价比较中，“最佳票价”和“一般票价”容易混淆。因为智能推荐路线不一定是最低票价路线，它可能因为时间、无障碍或节省阈值而选择常规路线。

因此，我将票价比较改为：

| 新字段 | 含义 |
| --- | --- |
| 最低票价 | 所有候选中最低价路线的票价。 |
| 推荐票价 | 智能推荐最终选择路线的票价。 |
| 一般票价 | 常规乘车路线票价。 |
| 节省金额 | 一般票价与推荐票价之间的差额。 |

相关变量：

```ts
const recommendedFare = routeInsight?.metrics.fare ?? routeResult.totalFare
const lowestFare = routeInsight?.alternatives.lowestFare?.fare ?? Math.min(recommendedFare, directFare)
const regularFare = routeInsight?.alternatives.regular?.fare ?? directFare
const savings = regularFare - recommendedFare
```

设计意义：

- 明确区分“算法找到的最低价”和“系统实际推荐的方案”。
- 避免用户误以为推荐票价永远等于最低票价。
- 更适合解释时间 / 票价折中场景。

### 7.3 推荐路线与常规路线时间对比

新增：

- 推荐路线预计耗时。
- 常规路线预计耗时。

用户可以同时比较：

- 推荐路线省多少钱。
- 推荐路线大约花多久。
- 常规路线大约花多久。
- 是否值得为了省钱而多出闸或多换乘。

## 8. 无障碍友好路线规划详细说明

### 8.1 用户需求

传统路线规划往往假设所有用户行动能力相同，但真实场景中存在大量差异：

- 老年人可能更依赖电梯。
- 轮椅用户需要无障碍通道。
- 游客和上班族可能携带大件行李。
- 家长可能推婴儿车。
- 行动不便者可能更希望减少复杂换乘。

因此，路线规划不应只考虑票价和时间，也应考虑站点设施条件。

### 8.2 实现方式

使用 `src/data/accessibilityData.json` 中的站点设施数据，在 `routeInsights.ts` 中计算每条路线的无障碍匹配度。

当用户选择：

- `off`：不计算无障碍惩罚。
- `prefer`：不强制，但对不满足条件的路线加较小惩罚。
- `require`：强制要求满足条件，不满足的路线会被过滤或赋予高惩罚。

### 8.3 推荐逻辑

当无障碍模式为 `require` 时：

```ts
if (preferences.accessibilityMode === 'require' && metrics.accessibilityProblemStops > 0) return false;
```

含义：

- 如果路线存在不满足无障碍条件的站点，该路线不可用。
- 系统会优先选择满足条件的候选路线。

当无障碍模式为 `prefer` 时：

- 不直接过滤路线。
- 通过 `accessibilityPenalty` 增加不满足条件路线的评分成本。
- 这样可以在“无障碍友好”和“票价 / 时间”之间做柔性平衡。

### 8.4 HCI 价值

该功能体现了包容性设计：

- 不把行动能力有限用户排除在路线优化之外。
- 提供更具体、更可操作的路线建议。
- 将“无障碍”从地图高亮功能扩展到路线决策逻辑。

## 9. 时间 / 票价折中路线详细说明

### 9.1 原有问题

最低票价路线并不一定适合所有用户。例如：

- 可能需要额外出闸再入闸。
- 可能增加换乘。
- 可能绕路。
- 可能节省金额很少但时间增加较多。

因此，只展示最低票价方案容易产生“算法正确但用户不想用”的问题。

### 9.2 新增方案

通过 `findRouteCandidateSet` 生成多种候选路线：

```ts
{
  lowestFare,
  regular,
  fastest,
  balanced
}
```

再由 `selectRecommendedRoute` 统一评估。

### 9.3 评分指标

时间 / 票价折中考虑：

- 总票价。
- 预计耗时。
- 出入闸次数。
- 换乘次数。
- 无障碍匹配度。

综合评分不是单纯票价，而是将多个成本映射到统一评分中。

### 9.4 用户价值

用户可以根据当前出行目的选择：

- 如果是学生或价格敏感用户，可以选择最低票价。
- 如果赶时间，可以选择更快路线。
- 如果只是日常出行，可以选择均衡路线。

该功能让系统更符合真实出行决策。

## 10. 少出闸 / 节省阈值模式详细说明

### 10.1 用户需求

票价优化路线常常依赖“分段出闸再入闸”。但这类方案存在额外成本：

- 多走路。
- 多次刷闸。
- 需要理解复杂路线。
- 可能增加迷路风险。
- 可能只节省很少金额。

因此，需要让用户控制自己能接受的复杂程度。

### 10.2 最大出入闸次数

用户可以选择：

- 不限。
- 0 次。
- 1 次。
- 2 次。
- 3 次。

该设置会进入路线搜索阶段和推荐过滤阶段。

路线搜索阶段：

- Dijkstra 状态中携带 `gateChanges`。
- 若下一状态超过 `maxGateChanges`，则不继续扩展。

推荐过滤阶段：

```ts
if (preferences.maxGateChanges !== null && metrics.gateChanges > preferences.maxGateChanges) return false;
```

### 10.3 最低节省金额

用户可以设置一个阈值，例如：

- 0 港币：只要能省钱就可以推荐。
- 2 港币：至少省 2 港币才推荐复杂方案。
- 5 港币：只有较明显节省才推荐额外出闸方案。

当路线节省低于阈值时：

- 如果常规路线可用，系统推荐常规路线。
- 在 `RouteInsight` 中记录 `suppressedSavings = true`。
- 前端可以展示“节省不足，已忽略复杂方案”的提示。

### 10.4 HCI 价值

该功能将用户的“麻烦感”转化为可配置参数，符合以下原则：

- 可控性：用户决定复杂程度。
- 鲁棒性：不推荐低收益高负担路线。
- 满意度：避免用户觉得系统“为了省一点钱而过度优化”。

## 13. 票价比较语义修正

### 13.1 问题发现

在实际测试中发现：

- 原“最佳票价”有时与“一般票价”相同。
- “节省金额”可能一直为 0。
- 原因是智能推荐结果不一定等于最低票价路线，有时会因为综合评分选择常规路线。

### 13.2 解决方案

将票价比较拆成三个概念：

| 概念 | 说明 |
| --- | --- |
| 最低票价 | 理论上找到的最低价候选路线。 |
| 推荐票价 | 系统综合用户偏好后最终推荐路线的票价。 |
| 一般票价 | 常规乘车路线的票价。 |

### 13.3 改进价值

该改动解决了概念混淆：

- 用户可以知道“最低能多少钱”。
- 用户也能知道“系统最终建议多少钱”。
- 当推荐路线不是最低价时，用户可以结合耗时和无障碍指标理解原因。

## 16. 当前实现的局限与后续改进方向

### 16.1 预计耗时仍是启发式估算

当前预计耗时基于：

- 默认等待时间。
- 每段路径跳数。
- 交通方式单跳耗时。
- 出入闸惩罚。

后续可以改进为：

- 接入实时班次。
- 使用线路真实运行时间。
- 根据换乘站距离估算换乘时间。
- 引入高峰期拥挤度。

### 16.2 出入闸次数口径仍可细化

当前出入闸次数按路线分段数计算：

```ts
segments.length - 1
```

该口径适合解释“额外分段次数”，但不等同于用户实际刷闸总次数。后续可以将 UI 文案进一步调整为：

- 额外出入闸次数。
- 分段乘车次数。
- 额外操作次数。

### 16.3 无障碍数据依赖静态数据

当前无障碍匹配基于静态设施数据。后续可以增加：

- 设施临时停用信息。
- 电梯维修公告。
- 用户反馈。
- 官方实时无障碍状态。

### 16.4 推荐权重可进一步用户化

当前权重是手动设定的经验值。后续可以：

- 根据用户历史选择自动调整。
- 提供高级设置。
- 使用用户研究结果校准权重。
